# Tablekeeper: Decisions

Why things are the way they are, as they stand now. Add new entries with the next number. When a decision changes, update or remove its entry rather than adding one that supersedes it; git history keeps the old reasoning. Numbers are never reused, since code and docs cite them. Details live in the docs each entry points to.

| ID | Decision | Why |
|---|---|---|
| D-001 | Board reading uses classic CV (opencv.js) in the browser, not a vision LLM | Fixed, known layouts make it a per-cell classification problem: free, offline, deterministic, measurable. A VLM costs per call and is weak at precise grid positions and counting. |
| D-002 | Every detected value is a draft with confidence; everything is editable; manual entry always available | Photos vary; a 97%-right scorer is useful only if the rest is quick to fix. Corrections are logged to measure real accuracy. |
| D-003 | Rules assistant navigates the rulebook with tools (table of contents, read section, full-text search), no embeddings | Rulebooks are short and structured; whole sections answer better than chunks, citations map to pages, and no vector store is needed. |
| D-004 | Rulebook PDFs stay out of git; extracted text lives in the database; the app links to the official PDF | Respects publishers' copyright in a public repo. |
| D-005 | Separate Express API (Render) and Next.js web (Vercel) sharing `packages/core` | Clear frontend/backend boundary; the API owns secrets, quotas and persistence; scoring is shared so the UI and API agree. Express over Hono for familiarity. Render's free tier slept, hence the keep-alive; since X2 both run on Vercel (D-072). |
| D-006 | Guests can use everything; sign-in (Google via Supabase) saves it; guest data isn't imported on sign-in | No login wall; one-tap sign-in when it adds value; less to build. |
| D-007 | Layered LLM protection: kill switch, global budget, per-user and per-IP quotas, rate limit, per-call caps, provider spend limit | The app is public; nobody should be able to exhaust the API budget. |
| D-008 | Games are modules in their own folders, pre-registered; shared code never branches on game id | Adding a game touches only its folders, which also lets one session build each game in parallel. |
| D-009 | Dorfromantik: the player reports unlocks; the advancement track isn't modeled | Unlock conditions differ per item and the track involves choices; asking is simpler and never wrong. |
| D-010 | One phone layout on every screen size, with a QR side note on desktop | It's a table-side companion; one layout halves UI work. A fake phone frame would read as a mockup. |
| D-011 | Each photo game ships sample photos ("Try Sample Photo") | Most visitors don't own the game. |
| D-012 | Tailwind + shadcn/ui over Material UI | The key screens are custom board editors; owned component code is easy to edit; avoids a Material look. |
| D-013 | Single-slice work runs on `slice/<id>` and parallel work uses Claude Code's built-in worktrees (`worktree-<name>`), automatic ports and the shared Agent Skills commands; every slice opens a PR and `/merge` rebase-merges it; the definition of done lives in AGENTS.md | Less tooling to maintain; the same PR workflow works for any single or parallel slice. |
| D-014 | UI text and visuals follow written "look and voice" rules (no dashes, emoji, filler or AI branding; short Title Case labels; drawn game motifs; flat warm styling), with the mechanical ones linted | The app should read as made by a player, not generated from a template. |
| D-015 | Conventional Commits are part of the definition of done, enforced by a commit-msg hook and a branch check | Readable history and scoped commits make parallel merges and reviews easier. |
| D-016 | Patchwork supports the red and gray boards; the board color is detected and switchable; each cell is compared against that board's empty references at all four rotated positions, so the board's orientation isn't needed | The boards have printed shading that varies by position, and a nearly full board doesn't show enough empty cells to tell which way it's turned. Details: `docs/games/patchwork.md` → Boards and Photo reading. |
| D-017 | Azul photo detection (A2) is deferred; Azul is a manual round-by-round tracker (A1); its fixtures are still labeled for a later attempt | The Master Chocolatier wall prints each chocolate's image on its space, so empty and occupied spaces look alike in a photo. Details: `docs/games/azul.md` → Board, `docs/slices/A2-azul-detection.md`. |
| D-018 | TypeScript is pinned to 6.0 | typescript-eslint doesn't support TypeScript 7 yet. |
| D-019 | Workspace packages ship TypeScript source; Next.js transpiles them and the API is bundled with tsup | No per-package build step; one Render build bundles everything the API needs. |
| D-020 | Package boundaries are linted by package name and by relative path | Catches both kinds of import; cv may import only types from core. Details: `eslint.config.js`. |
| D-021 | `GameUiModule` lives in `apps/web/src/games/types.ts`; every member except `Motif` is optional | It needs React types; game slices add their Editor, ScoreFlow and the rest. |
| D-022 | The browser uses plain `supabase-js` (PKCE, session in localStorage under `tk:auth`), no server-side auth | Data goes through the API with a bearer token. E2E tests sign seeded users in by password and put the session under that key. |
| D-023 | `game_id` columns are checked against an id pattern, not the list of games | S1's `_example` game can be saved in tests; the API validates ids against the registry. |
| D-024 | `pnpm db:start` and `pnpm db:reset` refuse to run in a worktree | Every worktree shares one local database. |
| D-025 | opencv.js is never imported statically; cv takes a loader (`setOpenCvLoader`): Node requires it, the browser fetches the emitted asset and evaluates it. cv types it through its own subset (`packages/cv/src/pipeline/opencv.ts`) | Bundlers can't resolve its Node-only `require("fs")` and Vitest's interop breaks its promise export; this keeps it out of every chunk with no `next.config.ts` change. The package's own typings are mostly `any` and fail the strict lint. |
| D-027 | Cell stages work on typed arrays copied out of the board `Mat`; only image-level stages touch opencv memory | Features, classification and calibration stay plain TypeScript and can't leak; the tracker covers the rest. |
| D-028 | CV detection times out after 20s without a progress event (not 20s overall), terminating the worker; an abort resolves as `failed` | A slow first opencv download on a phone shouldn't be cut off while it's advancing; keeps `CvError` as S0 defined it. |
| D-030 | One rules question is one quota request, however many model calls it takes; `gateway.run` hands a callback the timed, recorded model | Quotas count what users ask, not how the agent works it out. |
| D-031 | The rules agent's final `answer` tool is required by the prompt (with `strict` schemas), not by a forced `tool_choice`; the tool list never changes within a run | Current Claude models reject a forced `tool_choice`, and thinking blocks are bound to the tool list (changing it returned a 400). Details: `docs/ARCHITECTURE.md` → Rules assistant. |
| D-032 | An answer that cites nothing it read is marked `notCovered` | An uncited claim is never shown as "From the Rulebook". |
| D-033 | Rules model is `LLM_MODEL_RULES`, defaulting to `claude-opus-5-5` at medium effort with the server-side refusal fallback; `RULES_MAX_OUTPUT_TOKENS=800` | Smoke runs took 4 to 11 seconds and about 7,000 input tokens per question; 800 output tokens was enough. |
| D-034 | Both quota functions lock usage rows global first | Concurrent requests deadlocked when the order differed. |
| D-035 | Rulebook ingestion splits sections by heading size with per-game layout settings in `scripts/lib/rulebook-layouts.ts`; text smaller than the body is dropped | None of the four PDFs has an outline. Font ids belong to the exact PDF version, so a new rulebook version needs that file reviewed. |
| D-036 | API tests send a forwarded IP (trusted through `trust proxy`) with their own `IP_HASH_SALT` and clean up their usage rows | Every test starts with a fresh guest quota and leaves the global row as it found it. |
| D-037 | `DetectionMeta` keeps S0's frozen shape: `corrected` holds the state paths that differ between the photo draft and the saved board (`cells.4`), `detected` counts the draft's confidence entries; manual entry saves no meta | One key space covers cells and fields and gives an accuracy rate; shared code can't map a game's confidence keys to its state. Details: `docs/ARCHITECTURE.md` → API. |
| D-038 | Session request schemas accept any id matching the database pattern and strip unknown keys; response schemas accept only registered ids | An unknown game is `NOT_FOUND` from the registry, and a client-sent `scoreTotal` or `breakdown` never reaches the service. |
| D-039 | `defineGame<State>()` erases a game's state type for the registry; shared code scores only state it parsed with that game's schema | Typed games fit one registry without shared code branching on game id. |
| D-040 | The example game isn't a `GameId`: its id is cast, `getGame`/`isGameId` find it only when `enableExampleGame(true)` has been called (from `apps/api/src/config.ts`, `apps/web/src/games/registry.ts` via `isExampleGameEnabled()` in `lib/env.ts`, or tests), and the web registry adds it through a widened view of `GAME_UI`, with the cv example detector | `kit/types.ts` stays frozen, the casts stay inside the example game, and `packages/core` stays completely free of `process.env`. |
| D-041 | Guests' `LocalStore` keeps only in-progress sessions and campaigns, and its history is always empty; a finished guest result reaches an account only through the pending save after sign-in | Guest data isn't imported on sign-in (D-006); nothing finished is stored on the device. |
| D-042 | The score flow state is read with `useSyncExternalStore` from sessionStorage, and cleared without a re-render after a save | The server render shows a skeleton; clearing silently keeps the result step from treating the board as lost before the saved game opens. |
| D-043 | E2E tests that sign in create and delete their own user per worker instead of sharing `e2e@local` | S0's sign-out test signs that user out everywhere, ending other files' sessions when they run in parallel. |
| D-044 | A game's first real state has no `upgrade`: Patchwork and Harmonies are version 1, Azul and Dorfromantik stayed at 0 | S0's placeholder state (version 0, `z.unknown()`) could never be scored or saved, so nothing stored needs upgrading. The next shape change for any game bumps its version with a tested upgrade step. |
| D-045 | Patchwork's 9×9 board drops the shared cell's 44px minimum so spaces stay square (about 38 to 43px); arrow keys and labels still reach every space | Nine 44px spaces don't fit a 360 to 430px column. |
| D-046 | Patchwork confidence keys are `"row,col"` for spaces plus `board`, `tokens.one` to `tokens.twenty` and `specialTile` (`PATCHWORK_FIELD_KEYS`) | P2 and P3 report detections against these keys and the editor outlines low-confidence ones. |
| D-048 | Game names exported through the core barrel carry the game's name wherever another game could use the same word (`HarmoniesPiece`, `HARMONIES_STACKS`, `harmoniesRiverPoints`) | Every game exports from `packages/core/src/index.ts`, and Harmonies and Dorfromantik both have rivers. |
| D-050 | A guest's finished Azul game stays on the device as in progress (`finished: true`) until they sign in to save it or tap Don't Save; guest games are found through ids under `tk:v1:azul:in-progress` in `localStorage` | Without it the final score is lost on reload, since guests can't save finished games (D-041). |
| D-052 | Dorfromantik's scorer reads only the game state, never the campaign: the sheet drops rows the campaign doesn't show before saving, and a save writes the session, then the campaign (a first game creates the campaign first, since the session links to it) | Undoing an unlock later never changes a past score, and a retry after a failed campaign write doesn't save the game twice. |
| D-054 | The privacy page names GitHub issues as the contact and doesn't describe data deletion | The owner's choice; issues are public, so the page says not to post personal details. Details: `docs/PRODUCT.md` → Privacy page. |
| D-055 | Photo scoring is off unless `NEXT_PUBLIC_ENABLE_PHOTO_SCORING=true`: the score home disables Take Photo, Upload Photo and sample photos and points to manual entry; Playwright turns it on | A deploy can hide the photo buttons until its detectors work in production. |
| D-056 | The server status line shows nothing when `/health` fails or is blocked, and waits 2500ms before showing "Waking up the server." | The page can't tell an ad blocker from a down API, and each feature already reports its own failed calls. The API client retries once after 1500ms, so a blocked `/health` settles just after that and would flash the waking line; a real Render cold start takes far longer. Superseded by D-074. |
| D-058 | The CV worker finds detectors through `findDetector(id)` in `apps/web/src/games/detectors.ts`, which imports each game's `games/<gameId>/detector.ts`; it never imports the game UI registry. Vercel builds with its default command (Turbopack) | Importing the UI registry pulled every game's React UI into the worker and led back to the worker itself: Turbopack's production build hung, the webpack build's worker crashed on `document`, and `next dev` never showed it. A game's detector lives in its own folder, so adding one edits no registry. |
| D-060 | Two guards keep the worker buildable: `cv-worker-imports.test.ts` (in `pnpm test`) fails if the worker's import graph reaches `.tsx`, React, Next, `games/registry.ts` or `lib/cv-client.ts`; `pnpm test:build` makes the real production build with `NODE_ENV=production` and runs `tests/e2e/S4.spec.ts` against `next start` | `next dev` never showed the production failure. |
| D-061 | Dorfromantik unlocks: one campaign entry per Red Heart; saving reads the campaign fresh and applies `addUnlocks`; the picker shows once per finished game ("No Unlocks" just closes it); "Start New Campaign" sits at the foot of the campaign page and clears the sheet flow; a guest's new campaign replaces the old one instead of archiving it (D-041) | Each heart can be undone alone, a stale page can't overwrite another tab's change, and nothing from an old campaign carries over. |
| D-063 | `playwright.config.ts` sets `RATE_LIMIT_MAX` high for the e2e API server | Every e2e test calls the API from localhost and shares one burst bucket (60 a minute); a full run went over and unrelated tests failed with load errors. |
| D-064 | Harmonies' "Reread Photo as Side X" runs the plain TypeScript reading on the main thread at the known corners, loaded on demand, instead of going through the CV worker | `DetectOptions` is frozen in `kit/types.ts` and the worker protocol can't carry a side; with known corners no opencv is needed. |
| D-065 | cv imports only types from core, so a cv game folder may repeat constants it needs from core (layouts, piece codes) as long as a test fails when they drift | Keeps the worker bundle free of core's runtime. Harmonies' guard is `apps/web/src/games/harmonies/detector.test.ts`. |
| D-066 | A Harmonies photo draft gives each stack the shortest valid height for its top color, with confidence 0 on its `"q,r:height"` key so the review banner counts it until the player sets it | Height can't be read from above. Details: `docs/games/harmonies.md` → Photo reading. |
| D-067 | Patchwork's detector reads raw LAB shifted by the board frame's color difference instead of `normalizeLighting`, and takes the board color from the frame's a* | Gray-world white balance pulls the red board to neutral (15 and 17 errors per board); the frame is the same material in every photo. Details: `docs/games/patchwork.md` → Photo reading. |
| D-068 | Patchwork's calibration lives in its own `references.json` (per board, per position empty references) built by `cvGame.calibrate`; its `cvGame.measure` rejects, so no generic S2 `profile.json` can be built for it. Its `read` adds a `board` pseudo-cell, so the eval counts 82 values per photo | Per-position references don't fit class centroids, and board color errors show up in the same eval as space errors. |
| D-070 | Switching Patchwork's board color rereads the photo with `hints.board` (confidence 1), keeps the chits and special tile, and disables the board section while it runs | `reread` replaces the whole state, and taps during it would be silently overwritten. Details: `docs/games/patchwork.md` → Photo reading. |
| D-071 | Patchwork chits are read beside the board: gold 1 chits counted by area, the purple 5, 10 and 20 chits and the special tile by template match against the reference crops (`chits.json`) plus their shape; an unreadable region (touching or overlapping chits) flags every count and warns; counts are eval pseudo-cells | Touching 1 chits are the common case and area counts them without splitting; 5 and 10 chits look alike at photo scale but differ in length. Overlaps can't be read reliably, so the player is asked to check rather than shown a confident wrong total. Details: `docs/games/patchwork.md` → Photo reading. |
| D-072 | The API deploys through Vercel's Build Output API: `pnpm build:vercel` bundles `src/vercel.ts` and every dependency into one CommonJS function and routes every path to it (`maxDuration` 60s) | Zero-config Express detection would pick `src/app.ts` (no default export), and its docs don't say whether workspace TypeScript source is compiled; building the output ourselves deploys exactly what `vercel.test.ts` loads. Details: `docs/DEPLOYMENT.md` → Vercel (API). |
| D-073 | The burst limit counts in Postgres (`rate_limit_hits`, one statement per hit) through a small `express-rate-limit` store keyed by the salted IP hash; `RATE_LIMIT_STORE` is `database` in production and `memory` elsewhere; a store error fails the request | Serverless instances share no memory. Supabase adds no service or dependency (Upstash would), at one RPC per `/v1` request; dev and e2e stay as they were. |
| D-074 | The server status line shows only "You're offline." and nothing calls `/health` on load (supersedes D-056) | The API on Vercel doesn't sleep, so there is nothing to wake; each feature reports its own failed calls. |
| D-075 | Agent work moves toward checks over prose, CI, and PRs into a protected `main`, built as W slices; the direction lives in `docs/AUTOMATION.md` | Agents copy what the codebase shows and forget what docs say: three hard rules had already drifted (`process.env` outside config, a disable without a reason). Checks are free per run on a public repo; tokens are the scarce resource on two Pro plans. |
| D-076 | PR review is CI on every PR, Claude (GitHub app, subscription token) only on a label or shared-code changes, and Antigravity (`agy -p`) from a local script | Google retired the consumer Gemini CLI and Gemini Code Assist on GitHub in 2026, so there is no free bot reviewer; review tokens go where checks can't reach. |
| D-077 | Corrections are logged by pattern in `docs/CORRECTIONS.md`; a pattern becomes a check on its second occurrence, or on its first only if high-stakes and the owner agrees | A check written after one incident is an over-reaction that adds rules nobody needs; the log shows real patterns over time. Rules already written in the docs are enforced without waiting. |
| D-078 | Commands live once as Agent Skills in `.agents/skills/`, with `.claude/skills` a symlink to it | Antigravity and Claude Code both read the Agent Skills format, so one copy serves both and the two can't drift. Details: `docs/AUTOMATION.md` → Agents and budget. |
| D-079 | `.github/workflows/ci.yml` runs one `Checks` job (`typecheck`, `lint`, `lint:commits`, `test:unit`, `build`) on every push to `main` and PR; `vitest.config.ts` ignores `LocalEnvError` so unit tests need no `.env.local` or running Supabase, and `build` passes placeholder `NEXT_PUBLIC_*` URLs | The fast deterministic checks run in ~2 minutes without a database service; a single stable job name (`Checks`) is easy for W4's branch protection to require. |
| D-080 | Hard rules in `AGENTS.md` and `docs/CONVENTIONS.md` (`no-env-outside-config`, `no-raw-colors`, `no-game-id-branching`, `require-disable-reason`, `reportUnusedDisableDirectives`, `@anthropic-ai/sdk` import boundary, pure scorers in `packages/core/src/games/`, no `fetch` in web UI) are enforced in ESLint (`eslint-rules/rules.js`, `eslint.config.js`), and `pnpm lint` runs through `eslint-rules/baseline.js` (`eslint-rules/baseline.json`) | Error messages name the fix and doc section directly, and the baseline ratchet lets future rules land as errors for new code while existing counts may only shrink. Details: `docs/AUTOMATION.md` → Enforcement map. |
| D-081 | `pnpm check:repo` (`scripts/check-repo.ts`, `scripts/lib/check-repo/`) checks rule IDs (`docs/games/*.md` vs test titles, exempting `⚠️`/`VERIFY` rows), immutable migrations (`MIGRATIONS_DIR = 'supabase/migrations'`), forbidden files (`.env*` except `.env.example`, PDFs, `data/rulebooks/*`, images >2MB; also run on staged files in the `pre-commit` hook), and branch ownership against changed specs' `## Owns` globs plus additive-only edits to shared wiring hub files | Catches non-syntax repo invariants in CI and before commit, and verifies that parallel slice branches only edit what their specs own. Details: `docs/AUTOMATION.md` → Enforcement map. |
| D-082 | Session transcripts are graded for silent failures (W16): a script classifies first, a model judges only a sample, and findings become `trace` rows in `docs/CORRECTIONS.md` rather than direct skill or rule edits. Agents get `pnpm shot` (W15) before the CI screen map | The first pass (2026-11-16, 62 sessions) found that most waste was setup friction nobody corrected (worktree-guard refusals, a preflight reading a denied file, scratch files in the repo), and that it showed up in tool errors alone. Routing it through the log keeps the "repeat before check" rule. Details: `docs/AUTOMATION.md` → Target flow, `docs/slices/W16-session-grading.md`. |
| D-083 | `main` is protected (PR required, `Checks` required, linear history, rebase-only merge, no force pushes, `enforce_admins: true`, no docs-only exception); `/build` opens a PR on `slice/<id>` or `worktree-<name>` with verification and session metadata (`.github/pull_request_template.md`), and `/merge` rebases, adds `docs: merge <branch>` (updating `docs/ROADMAP.md`, `docs/DECISIONS.md`, `docs/CORRECTIONS.md` and cleaning up finished specs), waits for CI, and rebase-merges one PR at a time | Keeping shared-doc edits in `/merge`'s sequential commit avoids PR conflicts on `docs/ROADMAP.md` without generating it from deleted specs; `enforce_admins: true` prevents local sessions sharing the owner's GitHub credentials from pushing to `main` or merging a failing PR, with emergency bypass via `gh api`. | D-084 | `/harden` (`.agents/skills/harden/SKILL.md`) promotes a pattern logged twice in `docs/CORRECTIONS.md` (or once, if high-stakes and agreed) to the strongest check that fits, cleans up or baselines existing occurrences, updates the enforcement map and sets the rows to `promoted`. | D-085 | The API talks to Postgres with `postgres` (porsager) over TCP (`max: 5`, `fetch_types: false`, timestamps as strings, int8 as number).
