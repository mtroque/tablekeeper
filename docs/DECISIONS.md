# Tablekeeper: Decisions

Why things are the way they are. Add new entries and supersede old ones rather than rewriting them; git history records when. Details live in the docs each entry points to.

| ID | Decision | Why |
|---|---|---|
| D-001 | Board reading uses classic CV (opencv.js) in the browser, not a vision LLM | Fixed, known layouts make it a per-cell classification problem: free, offline, deterministic, measurable. A VLM costs per call and is weak at precise grid positions and counting. |
| D-002 | Every detected value is a draft with confidence; everything is editable; manual entry always available | Photos vary; a 97%-right scorer is useful only if the rest is quick to fix. Corrections are logged to measure real accuracy. |
| D-003 | Rules assistant navigates the rulebook with tools (table of contents, read section, full-text search), no embeddings | Rulebooks are short and structured; whole sections answer better than chunks, citations map to pages, and no vector store is needed. |
| D-004 | Rulebook PDFs stay out of git; extracted text lives in the database; the app links to the official PDF | Respects publishers' copyright in a public repo. |
| D-005 | Separate Express API (Render) and Next.js web (Vercel) sharing `packages/core` | Clear frontend/backend boundary; the API owns secrets, quotas and persistence; scoring is shared so the UI and API agree. Express over Hono for familiarity. Render's free tier sleeps, hence the keep-alive. |
| D-006 | Guests can use everything; sign-in (Google via Supabase) saves it; guest data isn't imported on sign-in | No login wall; one-tap sign-in when it adds value; less to build. |
| D-007 | Layered LLM protection: kill switch, global budget, per-user and per-IP quotas, rate limit, per-call caps, provider spend limit | The app is public; nobody should be able to exhaust the API budget. |
| D-008 | Games are modules in their own folders, pre-registered; shared code never branches on game id | Adding a game touches only its folders, which also lets one session build each game in parallel. |
| D-009 | Dorfromantik: the player reports unlocks; the advancement track isn't modeled | Unlock conditions differ per item and the track involves choices; asking is simpler and never wrong. |
| D-010 | One phone layout on every screen size, with a QR side note on desktop | It's a table-side companion; one layout halves UI work. A fake phone frame would read as a mockup. |
| D-011 | Each photo game ships sample photos ("Try Sample Photo") | Most visitors don't own the game. |
| D-012 | Tailwind + shadcn/ui over Material UI | The key screens are custom board editors; owned component code is easy to edit; avoids a Material look. |
| D-013 | Parallel work uses Claude Code's built-in worktrees, automatic ports and five generic commands; the definition of done lives in AGENTS.md | Less tooling to maintain; the same workflow works for any future slice. |
| D-014 | UI text and visuals follow written "look and voice" rules (no dashes, emoji, filler or AI branding; short Title Case labels; drawn game motifs; flat warm styling), with the mechanical ones linted | The app should read as made by a player, not generated from a template. |
| D-015 | Conventional Commits are part of the definition of done, enforced by a commit-msg hook and a branch check | Readable history and scoped commits make parallel merges and reviews easier. |
| D-016 | Patchwork supports the red and gray boards; the board color is detected and switchable; each cell is compared against that board's empty references at all four rotated positions, so the board's orientation isn't needed | The boards have printed shading that varies by position, and a nearly full board doesn't show enough empty cells to tell which way it's turned. Details: `docs/games/patchwork.md` → Boards, `docs/slices/P2-patchwork-board-detection.md`. |
| D-017 | Azul photo detection (A2) is deferred; Azul is a manual round-by-round tracker (A1); its fixtures are still labeled for a later attempt | The Master Chocolatier wall prints each chocolate's image on its space, so empty and occupied spaces look alike in a photo. Details: `docs/games/azul.md` → Board, `docs/slices/A2-azul-detection.md`. |
| D-018 | TypeScript is pinned to 6.0 | typescript-eslint doesn't support TypeScript 7 yet. |
| D-019 | Workspace packages ship TypeScript source; Next.js transpiles them and the API is bundled with tsup | No per-package build step; one Render build bundles everything the API needs. |
| D-020 | Package boundaries are linted by package name and by relative path | Catches both kinds of import; cv may import only types from core. Details: `eslint.config.js`. |
| D-021 | `GameUiModule` lives in `apps/web/src/games/types.ts`; every member except `Motif` is optional | It needs React types; game slices add their Editor, ScoreFlow and the rest. |
| D-022 | The browser uses plain `supabase-js` (PKCE, session in localStorage under `tk:auth`), no server-side auth | Data goes through the API with a bearer token. E2E tests sign seeded users in by password and put the session under that key. |
| D-023 | `game_id` columns are checked against an id pattern, not the list of games | S1's `_example` game can be saved in tests; the API validates ids against the registry. |
| D-024 | `pnpm db:start` and `pnpm db:reset` refuse to run in a worktree | Every worktree shares one local database. |
| D-025 | opencv.js is never imported statically; cv takes a loader (`setOpenCvLoader`): Node requires it, the browser fetches the emitted asset and evaluates it | Bundlers can't resolve its Node-only `require("fs")` and Vitest's interop breaks its promise export; this keeps it out of every chunk with no `next.config.ts` change. Details: `docs/slices/S2-cv-toolkit.md` → Decisions. |
| D-026 | cv uses its own typed subset of opencv (`packages/cv/src/pipeline/opencv.ts`) | The package's typings are mostly `any` and fail the strict lint. |
| D-027 | Cell stages work on typed arrays copied out of the board `Mat`; only image-level stages touch opencv memory | Features, classification and calibration stay plain TypeScript and can't leak; the tracker covers the rest. |
| D-028 | CV detection times out after 20s without a progress event (not 20s overall), terminating the worker; an abort resolves as `failed` | A slow first opencv download on a phone shouldn't be cut off while it's advancing; keeps `CvError` as S0 defined it. |
| D-029 | The worker finds detectors through `GAME_UI[gameId].detector`, plus `_example` outside production | One lookup for every game; the web game modules are small enough to pull into the worker. |
| D-030 | One rules question is one quota request, however many model calls it takes; `gateway.run` hands a callback the timed, recorded model | Quotas count what users ask, not how the agent works it out. |
| D-031 | The rules agent's final `answer` tool is required by the prompt (with `strict` schemas), not by a forced `tool_choice`; the tool list never changes within a run | Current Claude models reject a forced `tool_choice`, and thinking blocks are bound to the tool list (changing it returned a 400). Details: `docs/slices/S3-rules-assistant.md` → Decisions. |
| D-032 | An answer that cites nothing it read is marked `notCovered` | An uncited claim is never shown as "From the Rulebook". |
| D-033 | Rules model is `LLM_MODEL_RULES`, defaulting to `claude-opus-5-5` at medium effort with the server-side refusal fallback; `RULES_MAX_OUTPUT_TOKENS=800` | Smoke runs took 4 to 11 seconds and about 7,000 input tokens per question; 800 output tokens was enough. |
| D-034 | Both quota functions lock usage rows global first | Concurrent requests deadlocked when the order differed. |
| D-035 | Rulebook ingestion splits sections by heading size with per-game layout settings in `scripts/lib/rulebook-layouts.ts`; text smaller than the body is dropped | None of the four PDFs has an outline. Font ids belong to the exact PDF version, so a new rulebook version needs that file reviewed. |
| D-036 | API tests send a forwarded IP (trusted through `trust proxy`) with their own `IP_HASH_SALT` and clean up their usage rows | Every test starts with a fresh guest quota and leaves the global row as it found it. |
| D-037 | `DetectionMeta` keeps S0's frozen shape: `corrected` holds the state paths that differ between the photo draft and the saved board (`cells.4`), `detected` counts the draft's confidence entries; manual entry saves no meta | One key space covers cells and fields and gives an accuracy rate; shared code can't map a game's confidence keys to its state. Details: `docs/slices/S1-score-flow.md` → Decisions. |
| D-038 | Session request schemas accept any id matching the database pattern and strip unknown keys; response schemas accept only registered ids | An unknown game is `NOT_FOUND` from the registry, and a client-sent `scoreTotal` or `breakdown` never reaches the service. |
| D-039 | `defineGame<State>()` erases a game's state type for the registry; shared code scores only state it parsed with that game's schema | Typed games fit one registry without shared code branching on game id. |
| D-040 | The example game isn't a `GameId`: its id is cast, `getGame`/`isGameId` find it only when `isExampleGameEnabled()` (tests or `NEXT_PUBLIC_ENABLE_EXAMPLE_GAME=true`), and the web registry adds it through a widened view of `GAME_UI`, with the cv example detector | `kit/types.ts` stays frozen and the casts stay inside the example game. Core reads `process.env` there only, guarded so a bare worker treats it as disabled. |
| D-041 | Guests' `LocalStore` keeps only in-progress sessions and campaigns, and its history is always empty; a finished guest result reaches an account only through the pending save after sign-in | Guest data isn't imported on sign-in (D-006); nothing finished is stored on the device. |
| D-042 | The score flow state is read with `useSyncExternalStore` from sessionStorage, and cleared without a re-render after a save | The server render shows a skeleton; clearing silently keeps the result step from treating the board as lost before the saved game opens. |
| D-043 | E2E tests that sign in create and delete their own user per worker instead of sharing `e2e@local` | S0's sign-out test signs that user out everywhere, ending other files' sessions when they run in parallel. |
| D-044 | A game's first real state is version 1 with no `upgrade` | S0's placeholder state (version 0, `z.unknown()`) could never be scored or saved, so nothing stored needs upgrading. Set by P1. |
| D-045 | Patchwork's 9×9 board drops the shared cell's 44px minimum so spaces stay square (about 38 to 43px); arrow keys and labels still reach every space | Nine 44px spaces don't fit a 360 to 430px column. Details: `docs/slices/P1-patchwork-manual.md` → Decisions. |
| D-046 | Patchwork confidence keys are `"row,col"` for spaces plus `board`, `tokens.one` to `tokens.twenty` and `specialTile` (`PATCHWORK_FIELD_KEYS`) | P2 and P3 report detections against these keys and the editor outlines low-confidence ones. |
| D-047 | Earlier slices' tests no longer assume a particular game lacks a scorer: S0's e2e accepts "Coming Soon" or the score home, the registry test checks `stateVersion` 0 only for unscored games, and S1's 422 test picks any unscored game and skips once none is left | Each game slice would otherwise break the same assertions. |
| D-048 | Game names exported through the core barrel carry the game's name wherever another game could use the same word (`HarmoniesPiece`, `HARMONIES_STACKS`, `harmoniesRiverPoints`) | Every game exports from `packages/core/src/index.ts`, and Harmonies and Dorfromantik both have rivers. Set by H1. |
| D-049 | Azul's first real state stays at `stateVersion` 0, an exception to D-044 | S0's placeholder could never be saved and S0's registry test expects 0; a later shape change bumps it with an upgrade step. Set by A1. |
| D-050 | A guest's finished Azul game stays on the device as in progress (`finished: true`) until they sign in to save it or tap Don't Save; guest games are found through ids under `tk:v1:azul:in-progress` in `localStorage` | Without it the final score is lost on reload, since guests can't save finished games (D-041). Details: `docs/slices/A1-azul-manual-rounds.md` → Decisions. |
| D-051 | Dorfromantik's first real state stays at `stateVersion` 0, an exception to D-044 | As with Azul (D-049): S0's placeholder could never be saved and S0's registry test expects 0. Set by D1. |
| D-052 | Dorfromantik's scorer reads only the game state, never the campaign: the sheet drops rows the campaign doesn't show before saving, and a save writes the session, then the campaign (a first game creates the campaign first, since the session links to it) | Undoing an unlock later never changes a past score, and a retry after a failed campaign write doesn't save the game twice. Details: `docs/slices/D1-dorfromantik-scoresheet.md` → Decisions. |
| D-053 | Vercel builds the web app with `next build --webpack` until S4 moves detector loaders out of `GAME_UI`; D-029 is superseded once S4 is done | D-029 pulls every game's React UI into the CV worker, which leads back to the worker itself: Turbopack's production build hangs, and under webpack the worker crashes on `document`. `next dev` never shows it. Details: `docs/slices/S4-cv-worker-detectors.md`. |
