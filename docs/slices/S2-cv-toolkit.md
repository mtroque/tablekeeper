# S2: CV toolkit

**Status:** 🟨 · **Depends on:** S0

**Goal:** the reusable, tested pipeline that turns a phone photo into a flattened, normalized board with confidence-scored cells, plus the harness that measures it. Game detection slices then add only a layout, a profile and a small classifier.

## Owns
- `packages/cv/src/pipeline/**`, `packages/cv/src/index.ts`, `packages/cv/src/games/_example/`, `packages/cv/package.json`
- `apps/web/src/workers/cv.worker.ts`, the implementation of `apps/web/src/lib/cv-client.ts` (signature fixed by S0), `apps/web/src/lib/cv-client.test.ts`
- `apps/web/src/app/dev/cv/**` (a development-only harness page) and `apps/web/public/dev/cv/`
- `scripts/eval-vision.ts`, `scripts/make-example-fixtures.ts`, `data/fixtures/_example/` (synthetic images generated by a script)
- Root `package.json`: only the `eval:cv` script and the `tsx` and `jpeg-js` dev dependencies; `pnpm-lock.yaml` for those
- `tests/e2e/S2.spec.ts`

## Scope
Everything in `docs/ARCHITECTURE.md` → Computer vision: the stages, calibration profiles, the worker and `cv-client`, and `pnpm eval:cv` (including `--calibrate`). The `_example` detector reads the S1 example game's 3×3 board from synthetic images.

**opencv.js:** `@techstark/opencv-js` (the maintained npm build of opencv.js, pinned), loaded through one memoized `loadOpenCv()` that every caller shares. Node (tests, eval) and the worker use the same package.

**Stages** (`packages/cv/src/pipeline/`), each exported from the package root:
- Mat stages (`loadImage`, `findBoardQuad`, `warpToCanonical`, `normalizeLighting`, `findBlobs`, `matchTemplateRotInvariant`) take and return `Mat`s and delete everything they allocate; the caller deletes what it receives.
- `orderQuad`, `cellFeatures`, `classifyNearest` and `calibrateProfile` are plain TypeScript over numbers and typed arrays. `sampleCells` copies each cell's inset pixels out of the `Mat` into typed arrays, so no cell-level `Mat` outlives the call.
- `loadImage(input, { maxSide, orientation })`: `orientation` is the EXIF orientation (1 to 8). Browsers already apply it when decoding (`createImageBitmap`), so the worker passes nothing; the eval reads it from the JPEG with a small parser (`readExifOrientation`).
- `findBoardQuad(mat, { aspect, minAreaRatio })`: `aspect` is the board's long side over its short side, `{ min, max }`. Corners are refined by fitting a line to each side's contour points and intersecting neighbors. Fallback: a centered quad covering 80% of the image, `found: false`, and the warning "Couldn't find the board edges. Drag the corners into place."
- `runBoardPipeline(image, config, opts)` composes the stages for any grid board: load → find (skipped when corners are given) → warp → normalize → sample → features → classify. It returns corners in original image pixels, one `{ key, label, confidence }` per cell, and warnings. A game detector is that config (layout, canonical size, aspect bounds, profile) plus a function from cell labels to the game's state.
- `CvGame` (the contract each `packages/cv/src/games/<gameId>/index.ts` exports as `cvGame`): `detector`, the label schema, the expected class of each cell from a label, and what calibration needs. The eval script loads `packages/cv/src/games/<gameId>/index.ts` by path, so there is no cv registry to edit. `packages/cv/package.json` exports `./games/*` so a web `GameUiModule.detector` can lazy-load it.

**Calibration profile** (`games/<gameId>/profile.json`, validated with Zod on load): feature names, per-class centroid, spread and sample count, and a tolerance. `classifyNearest` uses the spread-scaled distance to each centroid; confidence is the margin to the runner-up times a falloff once the distance passes the tolerance.

**Eval** (`pnpm eval:cv <gameId> [--calibrate]`, `scripts/eval-vision.ts`): reads `data/fixtures/<gameId>/labels.json`, decodes JPEGs with `jpeg-js`, and reports the metrics in ARCHITECTURE. A cell counts as flagged when its confidence is below 0.6 (`LOW_CONFIDENCE`). Corner error is the largest corner distance over the board's longer side in the photo. Writes `data/fixtures/<gameId>/eval-report.md` (gitignored) and exits 1 below `accuracyThreshold`. `--calibrate` warps each fixture by its labeled corners, collects cell features by true class and writes the profile.

**`_example`:** a square cream board with a dark frame and a 3×3 grid; a covered space holds a red token. State is `{ cells: boolean[][] }` (rows top to bottom, `true` covered), confidence keys are `"row,col"`. `scripts/make-example-fixtures.ts` renders 24 seeded synthetic photos (rotation up to 30°, perspective skew, warm and cool tints, darkening, noise, varied tables) with `labels.json` (`label.grid` as rows of `#` and `.`, like Patchwork).

**Worker and client:**
- `cv-client` keeps one worker per page session, created on the first call. Messages carry an id; the image buffer is transferred. Progress events: `loading-opencv` (only while opencv loads), `finding-board` (skipped when corners are given), `classifying`.
- The 20s timeout restarts on every progress event, so a slow first opencv download isn't cut off while work is still advancing. On timeout the worker is terminated and the next call starts a new one.
- Results: no `Worker` support or no detector for the game → `unavailable`; timeout → `timeout`; an error in the worker or an aborted call → `failed`.
- The worker finds a game's detector through `GAME_UI[gameId].detector`. The `_example` detector is added to that lookup only outside production builds or when `NEXT_PUBLIC_ENABLE_EXAMPLE_GAME=true`, and is reached with `detectWith('_example', ...)`, since `GameId` doesn't include it.
- `cvStats()` reports how many workers this page created and how many times opencv loaded, for the harness and the e2e test.

**Harness page** `/dev/cv` (not found in production unless `NEXT_PUBLIC_ENABLE_EXAMPLE_GAME=true`): reads a synthetic `_example` photo with the real worker, shows the cells, the stage, and how long the main thread was paused at most during detection.

## UI states
Only the harness page, which is a development tool: idle, reading (current stage), result (3×3 grid with confidence), error (the `CvError` in words with "Try Again").

## Acceptance criteria
- [ ] On synthetic boards (rotated, perspective-skewed, tinted, darkened), corners are recovered within 2% of board size.
- [ ] After normalization, the same cell under warm and cool tints classifies the same.
- [ ] `_example` on synthetic fixtures: ≥ 98% cell accuracy, with an eval report.
- [ ] In the browser, detection runs without blocking the main thread and opencv loads once per page session.
- [ ] Tests confirm no leaked `Mat`s.

## Tests
- Leaks: a test helper wraps `cv.Mat` construction and every opencv call that returns a new `Mat`, records each one, and asserts all are deleted after each stage and after full pipeline runs (found board, fallback, given corners).
- `cv-client` unit tests with a fake worker: progress, result, timeout and restart, abort, unavailable.

## Out of scope
Real game layouts and profiles; the corner UI (S1).
