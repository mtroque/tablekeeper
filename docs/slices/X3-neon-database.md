# X3: Database on Neon

**Status:** ✅ · **Depends on:** X2

**Goal:** Move Postgres from Supabase to Neon (Vercel Marketplace), with the API using a plain SQL driver instead of supabase-js and PostgREST, so the database sits next to the Vercel-hosted API and one fewer platform is needed. Sign-in stays on Supabase Auth until X4.

## Scope
- **Driver and query layer.** Use `postgres` (`porsager/postgres`) over TCP with a small typed tagged-template `Db` interface in `apps/api/src/db/client.ts` (`createDb`, `createUserDb`, `createClients`). On Vercel Fluid compute, warm function instances keep a small connection pool (`max: 5`) to Neon's pooled connection string (`DATABASE_URL`), and the same TCP driver talks to local Docker Postgres offline without a WebSocket proxy. `timestamptz` values parse as raw strings (preserving microsecond precision for session cursors) and `bigint` values parse as `number`.
- **Typed rows (`apps/api/src/db/types.ts`).** Replace the generated Supabase PostgREST `database.types.ts` with `apps/api/src/db/types.ts`, generated by `pnpm db:types` from `information_schema.columns` on `public`.
- **Access control in the API and RLS backstop.** The API connects with `DATABASE_URL`. Every user-owned query in `apps/api/src/db/{profiles,sessions,campaigns}.ts` filters explicitly by the verified `userId`. As a database backstop, `createUserDb(service, userId)` runs each query in a transaction that executes `set_config('role', 'app_user', true)` and `set_config('app.user_id', userId, true)`. The new migration creates the non-superuser `app_user` role (granted to the database owner) and updates all RLS policies on `profiles`, `play_sessions` and `campaigns` to check `public.app_user_id()` (`nullif(current_setting('app.user_id', true), '')::uuid`) instead of `auth.uid()`. `app_user` has no access to `rulebooks`, `rulebook_sections`, `llm_usage`, `rate_limit_hits` or the service-only functions.
- **SQL functions kept.** `start_campaign`, `search_rulebook_sections`, `replace_rulebook`, `llm_consume_request`, `llm_record_tokens`, `rate_limit_hit` and `rate_limit_undo` stay in Postgres and are called with plain `select`. Full-text search (`search` generated `tsvector`, GIN index) is unchanged. `start_campaign` updates and inserts using `public.app_user_id()`.
- **Users without `auth.users`.** Move `supabase/migrations/` to `db/migrations/` and add `db/migrations/20261116120000_neon_database.sql`, which drops `on_auth_user_created` and `handle_new_user()`, drops the `auth.users` foreign keys on `profiles.id`, `campaigns.user_id` and `play_sessions.user_id`, and sets `user_id` defaults to `public.app_user_id()`. `optionalAuth` in `apps/api/src/middleware/auth.ts` ensures the signed-in user's `profiles` row on every authenticated request (`insert ... on conflict (id) do nothing`), deriving the initial display name from `user_metadata.full_name`, `user_metadata.name`, the email local part, or `'Player'`.
- **Burst limit store.** Rename `SupabaseRateLimitStore` to `PostgresRateLimitStore` in `apps/api/src/db/rate-limit-store.ts`, keeping the same `rate_limit_hit` / `rate_limit_undo` behavior (D-073).
- **Local dev, migrations and worktrees.** `pnpm db:start`, `pnpm db:reset` and `pnpm db:types` keep their names and worktree guards (`scripts/db.mjs`), plus `node scripts/db.mjs migrate` for forward-only migration runs (used in production). `scripts/db.mjs` applies `db/migrations/*.sql` in order using `postgres` (with an idempotent `auth` compatibility stub before historical migrations so migrations 1 to 4 apply cleanly on vanilla Postgres and Neon) and seeds `public.profiles` from `db/seed.sql` (plus any local `data/rulebooks/*.sections.json`). Local Supabase stays up for Auth until X4; `tests/e2e/helpers.ts` ensures the seeded test user exists in local Supabase Auth on sign-in.
- **Production.** Provision Neon (`sin1`, free plan) via Vercel Marketplace on `tablekeeper-api`, run migrations and load all four rulebooks into Neon, deploy `tablekeeper-api`, and update `docs/ARCHITECTURE.md`, `docs/DEPLOYMENT.md`, `docs/CONVENTIONS.md`, `docs/PRODUCT.md`, `README.md`, `.env.example` and `apps/web/src/app/privacy/page.tsx`.

## Open questions
Resolved:
- **Driver:** `postgres` (`porsager/postgres`) over TCP. Fluid compute keeps warm instances that reuse pooled TCP connections to Neon's PgBouncer endpoint, and the same driver connects to local Docker Postgres offline without needing a WebSocket proxy.
- **Migration runner:** plain SQL files in `db/migrations/` applied by a small runner in `scripts/db.mjs` (`schema_migrations` table), no external migration CLI needed.
- **Local DB:** Docker Postgres (started from the main checkout), keeping tests offline and free.
- **Local Auth until X4:** keep local Supabase running for Auth (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) until X4 replaces it with Neon Auth; `DATABASE_URL` points the API and scripts directly at Postgres.

## Decisions
- `postgres` (porsager) over TCP to Neon's pooled URL, `max: 5`, `fetch_types: false`, timestamps kept as strings (cursor precision), int8 parsed as number. Why: works offline against local Postgres, warm Fluid instances reuse connections, no WebSocket shim.
- RLS backstop through an `app_user` role and transaction-local `app.user_id` (`public.app_user_id()`), set by `createUserDb`; every user query also filters by `user_id`. Why: the pool connects as the owner, which bypasses RLS, so a non-owner role is switched to per transaction.
- Migration runner is `scripts/db.mjs` (`schema_migrations` table, one transaction per file), with an idempotent `auth` stub so the four Supabase-era migrations still apply on plain Postgres and Neon. Migrations stay immutable; the move to `db/migrations/` is a pure rename.
- Local database is a `tablekeeper` database inside the local Supabase Postgres (`DATABASE_URL` derived from `supabase status`), since local Supabase still runs Auth until X4.
- Profiles are created by `optionalAuth` on every authenticated request (`on conflict do nothing`), replacing the sign-up trigger.
- `SupabaseRateLimitStore` renamed `PostgresRateLimitStore`; behavior unchanged (D-073).
- New dependency: `postgres` in `apps/api` (zero dependencies).
